## 파트2 (10:30~11:30)

### @Autowired vs @Resource

| 구분 | @Autowired | @Resource |
| --- | --- | --- |
| 출처 | Spring 전용 | Java 표준 (JSR-250, 우리 프로젝트는 `javax.annotation.Resource`) |
| 찾는 기준 | **타입** 먼저 → 여러 개면 `@Qualifier`/`@Primary` → 필드 이름 | **이름(id)** 먼저 → 없으면 타입 |
| 쓸 수 있는 곳 | 생성자, 필드, 세터, 파라미터 | 필드, 세터 (**생성자 X**) |
| 기타 | `required = false`, `List<T>`로 여러 빈 한꺼번에 주입 가능 | 이름을 직관적으로 지정 |

```java
@Autowired                     // 타입으로 찾음 (Hello 빈이 2개 → 필드명 hello와 같은 id 선택)
Hello hello;

@Autowired
@Qualifier("helloCons")        // 같은 타입이 여러 개일 때 id로 좁힘 (단독 사용 X)
Hello hello2;

@Resource(name = "helloCons")  // 처음부터 id로 찾음
Hello hello3;
```

- **언제 뭘 쓰나**
  - 기본은 `@Autowired` (특히 생성자 주입: final로 불변, 테스트 쉬움)
  - 같은 타입 빈이 여러 개이고 **id로 딱 집어야 할 때** → `@Resource(name=...)` 또는 `@Autowired + @Qualifier`
- **주의**: `@Resource(name="...")`, `@Qualifier("...")`의 id는 그냥 문자열이라 오타를 컴파일러가 못 잡음
  - 오늘 `hellCons` 오타 → `NoSuchBeanDefinitionException: No bean named 'hellCons'` → 테스트 실행 전에 실패

### 오버라이딩 규칙 (`@Override`)

`@Override`: 부모 클래스·인터페이스 메서드를 재정의했다고 컴파일러에 알리는 표시 → 오타·시그니처 실수를 컴파일 오류로 잡아 줌 (없으면 새 메서드로 취급)

| # | 규칙 | 예시 |
| --- | --- | --- |
| 1 | 메서드 **이름** 같아야 함 | `print` → `print` |
| 2 | **매개변수**(개수·타입·순서) 같아야 함 | `print(String)` ✅ / `print(int)` ❌ (오버로딩이 됨) |
| 3 | **리턴 타입** 같아야 함 (자식 타입은 허용) | `Object get()` → `String get()` ✅ |
| 4 | **접근 제어자** 같거나 더 넓게 | `protected` → `public` ✅ / `public` → `private` ❌ |
| 5 | **예외**(checked) 같거나 더 좁게 | `IOException` → `FileNotFoundException` ✅ / → `Exception` ❌ |
| 6 | `static`, `final`, `private` 메서드는 오버라이딩 불가 | |

- 접근 범위: `public` > `protected` > (default) > `private`
- 인터페이스 메서드는 자동 `public` → 구현 클래스도 반드시 `public` (예: `StringPrinterBean.print()`)

| | 오버라이딩 | 오버로딩 |
| --- | --- | --- |
| 뜻 | 부모 메서드 **재정의** | 같은 이름으로 **여러 개 정의** |
| 매개변수 | 같아야 함 | 달라야 함 |
| 위치 | 부모 ↔ 자식 | 같은 클래스 안 |
| 예시 | `toString()` 재정의 | `Hello()`, `Hello(String, Printer)` 생성자 |

### 3.9 프로퍼티(Property) 파일을 이용한 설정 방법

**환경에 따라 자주 변경되는 내용의 분리**

| 구분 | XML의 Bean 설정 메타정보 | 프로퍼티 값으로 제공되는 설정 정보 |
| --- | --- | --- |
| 예 | 빈 구성, 의존 관계 | DataSource 빈이 사용하는 DB 연결 정보 |
| 언제 바뀌나 | 애플리케이션 구조가 바뀌지 않으면 **자주 변경되지 않음** | 동작 환경(개발, 테스트, 스테이징, 운영)에 따라 **자주 바뀔 수 있음** |

- 변경되는 **이유와 시점이 다르면 분리**하는 것이 객체지향 설계의 기본 원칙 → 설정에도 같은 원칙 적용
- 환경에 따라 자주 바뀌는 내용은 **properties 파일로 분리**하는 것이 가장 깔끔함
  - XML처럼 복잡한 구성이 필요 없고, **키와 값의 쌍**(`key=value`)으로 구성하면 됨

유니코드는 무엇인지, UTF-8과 어떤 관계
유니코드(Unicode)는 전 세계 거의 모든 문자를 컴퓨터에서 일관되게 표현하기 위해 만든 문자 집합(Character Set, 코드 포인트 목록)이고, UTF-8은 그 유니코드 문자(코드 포인트)를 실제 바이트(Byte)로 변환해 저장·전송하는 인코딩 방식(Encoding) 중 하나입니다.

### SpEL (Spring Expression Language)

- 런타임(실행 중)에 객체 그래프를 조회·조작하는 스프링 표현식 언어
- **언제**: `@Value`, XML 설정, Spring Security 표현식 등에서 값을 동적으로 계산하거나 꺼낼 때
- **할 수 있는 것**
  - 프로퍼티 값 읽기·가공: `#{'${...}'.split(',')}`
  - 다른 빈의 필드·메서드 호출: `#{myService.getDefaultTimeout()}`
  - 산술·논리·삼항 연산: `#{count > 10 ? '많음' : '적음'}`

| 표기 | 의미 |
| --- | --- |
| `${...}` | 프로퍼티 **치환** (properties 파일에서 값 가져오기) |
| `#{...}` | SpEL **표현식 연산** |

### `"#{'${app.namelist}'.split(',')}"` 해석 (안쪽 → 바깥쪽)

```java
@Value("#{'${app.namelist}'.split(',')}")
List<String> names;
```

| 순서 | 부분 | 하는 일 | 결과 |
| --- | --- | --- | --- |
| 1 | `${app.namelist}` | `values.properties`에서 `app.namelist` 값을 문자열로 가져옴 | `Java,SpringFW,SpringBoot` |
| 2 | `'...'` | SpEL 안에서 **문자열 리터럴**로 쓰려고 작은따옴표로 감쌈 | `'Java,SpringFW,SpringBoot'` |
| 3 | `.split(',')` | 자바 `String.split(",")` → 쉼표 기준으로 잘라 `String[]` | `["Java", "SpringFW", "SpringBoot"]` |
| 4 | `#{ ... }` | 이 안을 SpEL 표현식으로 평가하라는 표시 | |
| 5 | `List<String> names` | `@Value`가 배열을 `List<String>`으로 자동 변환해 주입 | `[Java, SpringFW, SpringBoot]` |

- 결과는 **properties 파일 값에 따라 달라짐** → 코드는 그대로 두고 파일만 바꾸면 됨
- properties를 읽으려면 XML에 `<context:property-placeholder location="classpath:values.properties" />` 필요 (없으면 `${...}`가 글자 그대로 남음)
